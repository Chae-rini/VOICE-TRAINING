## 검증 — 실제 녹음 32개로 앱 YIN vs Praat 비교 (2026-10-24)

자세한 내용은 `Validation/YIN_vs_Praat.md`.

- 자료: GPT 훈련 때 녹음 32개(약 18분, 48 kHz 무손실)와 Praat 프레임별 F0 108,013개. 음성 파일은 임시 폴더에만 풀었고 프로젝트에는 넣지 않음
- 도구: `Tools/PitchValidation/main.swift`(앱의 `PitchDetector.swift`를 그대로 컴파일), `plot.py`(그림)
- **피치 값은 거의 정확히 일치**: 큰 오류(GPE) 0.15%, 미세 오차 중앙 6.2센트, 녹음별 중앙 F0 차이 최대 1.51%
- **유성/무성 판정은 앱이 더 보수적**: 임계값 0.15에서 판정 일치 84.72%로 기준 85%에 근소하게 미달. 놓친 점은 주로 소리 시작·끝 가장자리
- 임계값 0.20이면 GPE는 그대로, 판정 일치 87.76%, 소리 한가운데에서 빠지는 점 7.9% → 4.9% → **0.20으로 적용함**
- 스무딩(5프레임 중앙값)은 정확도에 거의 도움이 안 됨

## 그래프·임계값 변경 (2026-10-24)
- `PitchDetector.threshold` 0.15 → 0.20 (위 검증 근거)
- 피치 그래프를 점에서 **꺾은선**으로 바꿈. 이웃한 점 사이가 50ms 이내면 선으로 잇고(점 하나 빠진 곳까지), 그보다 긴 무음은 끊어서 빈칸으로 둠. 선분마다 목표 범위 안이면 청록, 밖이면 회색. 앞뒤가 끊긴 외톨이 점은 작은 점으로 표시
- 선 끊기 규칙은 `PitchHistory.voicedSegments(maxGap:)`로 분리하고 테스트함

## 2단계 — 녹음 → 듣기 → 다시 녹음 연습 고리 (2026-10-25)
- 마이크 권한 문구(NSMicrophoneUsageDescription)를 프로젝트 설정에 추가 (사용자 요청). 시뮬레이터에서 권한 창에 문구가 그대로 뜨는 것을 확인
- "연습 시작" → 녹음(연습 시간만큼) → 방금 녹음 듣기 → 숨 고르기 3초 → 다시 녹음 … 을 **반복 횟수(1~10회, 기본 5회)**만큼 진행. 마지막에 "연습이 끝났어요. 목을 잠깐 쉬어 주세요." + 진동
  - 녹음이 끝날 때마다 가벼운 진동. 듣는 중에는 "건너뛰기"로 바로 다음 단계
  - 상태 줄: "녹음 중 · 2/5회 0:12", "방금 녹음 듣는 중", "숨 고르기 · 곧 3번째 녹음"
  - 듣는 동안 그 녹음의 피치 꺾은선을 소리와 같은 속도로 다시 흘려 보여줌. 큰 숫자도 재생 위치의 Hz
  - 연습이 끝난 뒤(또는 중간에 정지한 뒤) ▶ 버튼으로 마지막 녹음 다시 듣기
  - 듣는 동안에는 마이크 분석을 끔 (스피커 소리를 다시 분석하지 않게)
- 녹음은 메모리에만 둔다(최대 3분, 약 35MB). 파일 저장·네트워크 없음
- 오디오 세션에 `.defaultToSpeaker` 추가 (재생을 수화기가 아닌 스피커로)
- (2026-10-25, 아이폰 확인 후) **재생 소리가 작다는 피드백** → 재생할 때만 녹음을 키움. 녹음마다 가장 큰 순간이 약 −1 dBFS가 되도록 전체에 같은 배율을 곱한다(최대 +24 dB, 줄이지는 않음). 일그러뜨리는 압축은 쓰지 않음. 피치 분석은 원래 소리로 하므로 영향 없음
- (2026-10-25) **그래도 작다 → "70% 음량에서 정상으로" 요청** → 듣는 동안은 오디오 설정을 음악 앱과 같은 `.playback`으로 바꿈. 녹음은 그대로 `.measurement`. 설정이 다르므로 녹음 엔진과 재생 엔진을 따로, 단계마다 새로 만든다. 듣는 동안에는 마이크가 완전히 꺼짐(상태 표시줄 마이크 표시도 꺼짐)

## 목표 범위 기준 녹음 — 내 목소리를 먼저 재고 목표를 정한다 (2026-10-25)
- **내 목소리 재기 화면**: 처음 실행할 때 한 번 자동으로 뜨고("나중에"로 건너뛰기 가능), 그 뒤에는 목표 범위 아래 **"내 목소리 (다시) 재기"** 버튼으로 언제든 연다 (따로 설정 화면이 없어서 이 자리에 둠)
  - 연습 문장 하나("회의는 오후 두 시에 시작합니다.")를 10초 동안 두세 번 편하게 읽는다. 연습과 같은 YIN 분석
  - 결과는 **중앙값과 범위(아래 10%~위 10%)만** 보여 준다. 높다·낮다·성별 같은 평가는 하지 않는다
  - 목소리가 2초보다 짧게 잡히면 "목소리가 거의 잡히지 않았어요" + 다시 재기
  - **"녹음 파일로 재기"**도 있다 (음성 메모 등). 시뮬레이터에서는 이것으로 확인
- **내 기준 목소리** 저장: 중앙값·아래 10%·위 10%를 기기 안 설정(@AppStorage)에만 둔다. 공유 요청문에도 넣지 않는다
- **그래프**: 기준 중앙값을 **남보라색 얇은 점선 + "기준" 글자**로 표시. 청록색 목표 범위 띠(채운 사각형)와 색·모양이 다르다
- **처음 목표 범위 = 기준 중앙값 ±20 Hz** (5 Hz 단위, 70~400 Hz 안). 슬라이더로 위든 아래든 자유롭게 옮긴다
  - 결과 화면의 **"목표 범위를 이 기준에 맞추기"** 스위치로 정한다. 목표 범위가 저장돼 있으면 처음에 **꺼져 있어** 저장된 값은 직접 켜지 않는 한 바뀌지 않는다
  - 새로 설치한 사람은 목표 범위 **없이** 시작한다 (180~220 Hz처럼 한쪽 방향을 전제한 값을 쓰지 않음). 재기 전에는 띠가 없고 꺾은선은 모두 회색, 요약 카드의 "목표 범위 안"은 "–", AI 요청문에는 "아직 정하지 않음"
  - 예전 버전부터 쓰던 사람: 앱을 처음 켤 때 한 번 확인해서, 목표 범위를 따로 저장한 적 없어도 예전 설정(연습 시간·반복 횟수·문장 종류·대본 필터)이 하나라도 있으면 보던 180~220 Hz를 그대로 저장해 둔다
- **원칙 확인**: 목표 범위 가운데가 기준에서 **반음 6개 이상**(위·아래 어느 쪽이든) 떨어지면 "기준 목소리와 꽤 떨어진 범위예요. 목에 무리가 없는지 천천히 확인해 보세요."만 띄운다. 막거나 권하지 않는다

## 4단계-1 — 포먼트(F1·F2) 분석기 + 합성 모음 검증 (2026-10-25)
- 화면 변화 없음. 소리 조각 하나에서 F1·F2를 재는 `FormantAnalyzer`를 만들고 정답을 아는 합성 모음으로 검증했다
- 계산 순서 (외부 패키지 없음, Accelerate + 직접 구현)
  1. 48 kHz → 12 kHz로 줄이기 (저역 통과 필터 63탭 + `vDSP.downsample`)
  2. 고역 강조(0.97) → Hamming 창(42.7 ms) → 자기상관(`vDSP.dot`)
  3. Levinson–Durbin으로 LPC 계수 (토플리츠 연립방정식을 O(p²)로)
  4. LPC 다항식의 근: **Durand–Kerner 반복을 직접 구현** (아래 이유)
  5. 근의 각도 → 주파수, 반지름 → 대역폭. 90~5500 Hz, 대역폭 400 Hz 이하 중 낮은 순서로 F1, F2
- **LAPACK을 쓰지 않은 이유**: Accelerate의 예전 LAPACK(`dgeev_`)은 iOS 16.4부터 폐기 예정이라 빌드 경고가 나고, 새 LAPACK은 프로젝트 설정에 컴파일 옵션(`-DACCELERATE_NEW_LAPACK`)을 넣어야 한다 (SDK 헤더로 확인). 근 찾기는 40줄 정도라 직접 구현하고 정답을 아는 다항식으로 테스트했다. 근 방식이라 F1·F2가 붙은 '오'·'우'도 봉우리 찾기보다 잘 가른다
- **최대 포먼트 5500 Hz 하나만 쓴다**: Praat는 성인 여성 5500 Hz, 남성 5000 Hz를 권하지만 이 앱은 성별을 묻지 않는다 (원칙 3)
- **합성 모음 검증** (`Tools/FormantValidation`): 성대 음원(Rosenberg 펄스) → F1~F4 공명기로 7개 모음 비슷한 소리를 만들고 F0를 100~350 Hz로 바꿔 가며 잼. 모음별 포먼트 값은 상대 배치만 흉내 낸 시험용 값(특정 집단의 평균 아님)
  - LPC 차수·창 길이 비교 (14·12·10차, 42.7·25 ms): 차이는 작았고, **12차**가 목소리가 높을 때 F2를 가장 안정적으로 잡았다 (F0 350 Hz F2 최대 오차 14차 31% → 12차 11%). 10차는 F0 350 Hz에서 놓침. 창 길이는 거의 영향 없음 → **12차, 42.7 ms**로 정함
  - 결과(12차): F0 100 Hz — F1 최대 3.3%, F2 최대 1.2% / F0 150 Hz — F1 6.1%, F2 4.6% / F0 200 Hz — F2 3.2%, **F1은 최대 20%** / F0 250 Hz 이상 — F1 최대 36%, F2 최대 17%
  - 속도: 조각 하나에 약 7 µs (이 Mac 기준). 조각 간격(21 ms)의 0.03%라 오디오 스레드에서 돌려도 부담이 없다
  - 처음에는 단순한 성대 음원(펄스 + 고정 저역 통과)으로 만들어 F0 100 Hz에서도 F1이 +14% 틀렸다. 음원 스펙트럼의 봉우리가 F0와 상관없이 약 380 Hz에 고정된 탓이었고, 실제 목소리처럼 F0를 따라 움직이는 Rosenberg 펄스로 바꾸자 2~4%로 줄었다
- **알게 된 한계**: 목소리가 높을수록(F0 ≥ 200 Hz) F1이 낮은 모음('이'·'우'·'으'·'오')에서 F1이 가까운 배음(2×F0 등)으로 끌린다. 차수·창 길이로는 풀리지 않았다 (LPC의 알려진 성질). F2는 F0 250 Hz까지 대체로 10% 안
  - 4-2에 반영할 것: F0가 높고 F1이 2×F0 근처이면 F1을 "불확실"로 표시하거나 흐리게 그린다. 모음 지도는 F2(앞뒤) 방향이 더 믿을 만하다는 것을 화면에서 숨기지 않는다
- 테스트(새 6개): 설정값, Levinson–Durbin(AR(2) 계수 되찾기), 다항식 근, F0 100·150 Hz 7개 모음 F1·F2 8% 안, F0 200 Hz F2 5% 안, 무음·짧은 조각. 높은 목소리의 F1은 한계라 테스트로 보장하지 않는다
- 실제 녹음과의 비교(Praat)는 아직 하지 않았다. 이 Mac에 Praat가 없고, 예전 녹음 묶음에도 포먼트 값이 없다

## 3단계-3 — 두 녹음 비교 (2026-10-25)
- [기록] 탭 ‘남긴 녹음’에 **‘두 녹음 나란히 비교’** (남긴 녹음이 두 개 이상일 때). 누르면 비교 화면이 아래에서 올라온다
  - 처음에는 가장 먼저 남긴 녹음(A, 주황)과 가장 최근 녹음(B, 파랑)을 골라 둔다. 지금 보이는 기간·언어 안에 두 개 이상 있으면 그 안에서 고른다
  - A·B는 남긴 녹음 전체에서 다시 고를 수 있고, ‘A와 B 바꾸기’가 있다
- **나란히 보기** (표): 남긴 때, 말한 언어, 길이, 중앙, 범위(아래 10%~위 10%), **높낮이 폭**(범위를 반음으로 센 값, 12·log₂(위/아래)), 그때 목표 범위, 목표 범위 안 비율, 목소리 잡힌 시간
  - 아래에 한 문장: "B의 중앙값이 A보다 12 Hz 높아요 (반음 약 1.3개)." 높다·낮다는 사실만 말하고 좋아졌다·나빠졌다는 말은 하지 않는다 (원칙 3). 1 Hz 미만이면 "거의 같아요"
- **높이 분포** 그래프: 두 녹음 파일을 기기 안에서 다시 분석해(연습과 같은 YIN), 각 높이(5 Hz 간격)에 머문 비율을 겹쳐 그린다. 점선은 각 녹음의 중앙값, 청록 띠는 지금 목표 범위. 가로축은 두 녹음의 아래 2%~위 2%와 목표 범위가 들어가게 맞춘다 (드물게 튄 값은 뺌)
- **듣기**: ‘A 듣기’, ‘B 듣기’(누르면 다른 쪽은 멈춤, 다시 누르면 멈춤), **‘A → B 이어 듣기’**(A가 끝나고 0.7초 쉰 뒤 B), 남은 시간과 ‘멈추기’
  - 두 녹음 모두 가장 큰 소리를 같은 크기로 맞춰 들려준다 (연습 다시 듣기와 같은 규칙). 그래서 음량 차이는 비교되지 않는다고 화면에 적었다
  - 연습 중이면 듣기를 막고, 연습이 시작되거나 앱이 백그라운드로 가거나 화면을 닫으면 멈춘다. 전화·알람으로 끊겨도 멈춘다
  - 재생은 연습용 AudioInputManager와 따로 `ComparePlayer`가 맡는다 (같은 .playback 설정, 끝 감지는 취소할 수 있는 타이머)
- 소리 파일을 읽지 못하면 그쪽은 숫자만 비교하고 주황 글씨로 알린다
- 계산 규칙(처음 짝, 높낮이 폭, 중앙값 차이 문장, 분포, 가로축)은 `RecordingComparison.swift`에 두고 테스트했다. [기록] 탭 그래프의 축 규칙을 함께 쓰도록 `PracticeHistory.pitchDomain(values:)`로 나눴다

## 높이 그래프를 반음 눈금으로 (디자인 ③, 2026-10-25)
- **문제**: 높이 그래프가 Hz 직선 눈금이었다. 사람의 음높이 감각은 비율(반음) 단위라, 같은 "반음 4개" 흔들림이 260 Hz에서는 110 Hz보다 2.4배 넓게 그려졌다. 낮은 목소리는 실제 느낌보다 납작하게, 높은 목소리는 크게 보였다 — 어느 방향도 기본으로 두지 않는다는 원칙 3과도 어긋났다
- **바꾼 곳 (Hz 높이를 그리는 세 곳)**
  - [높이] 그래프와 목표 범위 슬라이더: 세로축 위치를 반음(로그) 눈금으로. 슬라이더도 같은 눈금이라 낮은 쪽에서 손가락이 덜 민감하지 않다. 저장값은 그대로 Hz, 5 Hz 단위, 70~400 Hz
  - [기록] 탭 ‘연습마다 높이’ 그래프: 세로축을 로그 눈금으로. 위아래 여유(반음 1.5개)와 최소 폭(반음 6개)도 반음으로 센다 — 예전 Hz 여유(15 Hz)는 낮은 목소리에게 상대적으로 큰 여유였다
  - 두 녹음 비교 ‘높이 분포’: 가로축을 로그 눈금으로, 분포 칸을 5 Hz에서 **반음 반 칸**(440 Hz 기준 고정 경계)으로. 5 Hz 칸에서는 같은 반음 2개 흔들림이 300 Hz 목소리에서 120 Hz 목소리보다 2배 넘는 칸에 퍼졌다
- **눈금 숫자는 Hz 그대로** (70·100·150·200·300·400, 좁은 범위면 더 촘촘한 묶음). 음이름(C3 등)은 쓰지 않았다
- **목표 범위의 폭을 반음으로**: ‘조정’을 펼쳤을 때만 "목표 범위의 폭은 반음 13.7개예요."를 보여 준다. 평소 한 줄에는 넣지 않았다
- 계산은 새 파일 `PitchScale.swift` 한 곳에 모았다 (반음 거리, 반음 옮기기, 로그 눈금 위치, 눈금 숫자 고르기). `VoiceBaseline`의 반음 거리도 이것을 쓴다
- 바꾸지 않은 것: 모음 지도(F1·F2) 축 — 다음 단계로 따로. 저장값, 목표 범위 규칙(기준 ±20 Hz), 색

- 원인: `TakeRecorder`는 최근 N초만 보관하는데 피치 기록(`history`)은 N+2초를 보관했고, 요약 카드가 `history` 전체로 요약을 만들었다. 소리에 없는 앞 2초가 중앙값·범위·목표 비율에 섞였다
- 재현: 20초 발성(앞 10초 100 Hz, 뒤 10초 200 Hz), 최근 10초 보관 → 고치기 전 아래 10%가 100 Hz, 목표(190~210) 안 83%, 목소리 시간 12초
- 고침: 녹음을 확정할 때 소리의 첫 샘플~마지막 샘플 시각에 든 점만 잘라 녹음 묶음(`RecordedTake`)에 넣는다. 요약은 묶음의 점으로 만든다 → 아래 10% 200 Hz, 목표 안 99% 이상, 목소리 시간 10초 이하

**버그 ② 기준·모음 재기가 마지막 녹음의 수치를 덮어쓴다**
- 원인: 재기도 `beginRecording()`을 거쳐 `history`를 새로 만드는데 마지막 녹음(소리·제목·길이)은 그대로였다. 녹음 A → 재기 B 뒤에 A를 보거나 저장·공유하면 소리는 A, 수치는 B
- 재현: A(150 Hz) 녹음 → B(250 Hz) 재기 → 고치기 전 A의 요약·공유 요청문·저장된 중앙값이 250 Hz, 그래프도 B
- 고침: `RecordingTimeline`이 화면 그래프용(`display`, 여유 2초 포함), 재기용(`measurement`), 마지막 녹음 묶음(`lastTake`)을 따로 담는다. 재기는 재기용만 쓰고, 끝나거나 중간에 멈추면 그래프를 마지막 녹음으로 되돌린다. 요약 카드·기록에 남기기·AI 공유·다시 듣기는 모두 묶음을 쓴다. `saveLastTake`는 화면에서 요약을 넘겨받지 않고 묶음에서 직접 만든다
- 묶음 타입은 `Models/`에 두었다 (`AudioInputManager`가 커지지 않게)

**버그 ③ 저장에 실패해도 "기록에 남겼어요"가 뜬다**
- 원인: `PracticeArchive.save()`가 `try?`로 오류를 버렸고, `isTemporary`는 화면에서 쓰지 않았다
- 고침
  - `save()`와 남기기(연습·녹음·기준·모음)·지우기가 오류를 던진다. 실패하면 `rollback()`으로 바꾼 내용을 되돌린다 (목록에 저장 안 된 기록이 보이거나 나중에 저절로 저장되지 않게)
  - 녹음: m4a를 만든 뒤 기록 저장에 실패하면 m4a를 지운다. 지울 때는 기록을 먼저 지우고 저장에 성공한 뒤 파일을 지운다
  - 화면: 영구 저장에 성공한 뒤에만 "연습 기록을 남겼어요"·"기록에 남겼어요"를 보인다. 실패하면 "기록을 저장하지 못했어요. 저장 공간을 확인해 주세요." (기준 재기 화면, 모음 재기 안내, [기록] 탭 지우기 실패 알림도)
  - 기준·모음 재기는 이력 저장을 먼저 하고, 실패하면 기준·목표 범위·내 모음 지도도 바꾸지 않는다
  - `isTemporary`면 [기록] 탭 위에 "이번 실행 동안만 기록이 유지돼요" 안내
  - ‘기록에 남겼어요’를 Bool 대신 저장된 기록의 ID로 판단한다. [기록] 탭에서 그 녹음을 지우면 [높이] 탭이 다시 ‘기록에 남기기’를 보여 준다 (화면은 `@Query` 목록으로, 저장 함수는 `recordingExists`로 확인)
- 테스트용으로 `PracticeArchive.simulatedSaveError`(Debug 빌드에만 있음)를 두어 저장 실패를 흉내 낸다

## [높이] 그래프 고정 + 가로축 = 들려줄 길이 (2026-10-25)
아이폰 테스트 피드백: 대본을 내려 읽으면 그래프가 화면 밖으로 밀려나고, 그래프가 10초로 고정이라 10초가 지나면 앞 기록이 사라졌다.
- **그래프 고정**: [높이] 화면에서 큰 숫자와 그래프를 위에 고정하고, 그 아래(목표 범위 줄·요약 카드·말하는 언어·문장·대본)만 스크롤한다. 목표 범위 줄은 그래프에서 떼어 `TargetRangeControls`로 나눴다
- **대본 읽기 모드**: 문장 종류가 ‘대본’이면 그래프를 220 → 150pt로 낮추고 큰 숫자를 한 줄로 작게("152 Hz · 현재 목소리 높이"). 대본 상자는 170 → 240pt(글자 크기에 맞춰 커짐)
- **가로축 = 들려줄 길이**(10초~3분): `Models/GraphWindow.swift`. 처음에는 요청대로 "왼쪽 시작선부터 채우고 다 차면 흐르기"로 만들었다가, 사용자 요청("시간과 선이 반대가 됐으면, 피치 읽기에 더 직관적")으로 **오른쪽 끝 = 지금, 곡선과 시간 눈금이 함께 왼쪽으로 흐르기**로 바꿨다. 곡선의 머리가 한자리에 있어 지금 높이를 읽기 쉽다. 보이는 구간(최근 N초)은 녹음 통이 남겨 두는 소리, 곧 다시 들을 수 있고 요약 수치를 내는 구간과 같다 (테스트로 확인)
- **시작선**: 녹음을 시작한 때에 실선 "시작", 반복 루프에서 다시 녹음하면 점선 "2번째"·"3번째". 들려줄 길이보다 오래 녹음하면 왼쪽 밖으로 나간다. 막 시작해 오른쪽 끝에 있을 때는 글자를 선 왼쪽에 붙인다
- **시간 눈금**: 녹음 시작부터 센 분:초("0:30"). 눈금 간격은 눈금이 6개 이하가 되는 가장 촘촘한 값(2·5·10·15·30·60초 → 10초 그래프는 2초, 1분은 10초, 3분은 30초 간격). 녹음 시작 전(시작선 왼쪽의 빈 곳)에는 눈금이 없다
- **다시 듣기**: 녹음이 끝난 때를 오른쪽 끝으로 녹음 전체를 그대로 두고, 재생 위치 세로선이 같은 축 위를 지나간다. 아직 재생하지 않은 뒷부분은 흐리게. 멈춘 화면도 녹음하던 화면이 멈춘 모습 그대로라 그래프가 튀지 않는다
- **점 줄이기**: 화면 폭보다 촘촘한 점은 같은 픽셀 열마다 하나(그 열의 목소리 높이 평균)로 묶어 그린다. 3분이면 점이 8천 개가 넘지만 그리는 점은 픽셀 수 이하. 무음 칸이 끼면 선을 끊는다 (`PitchHistory.displaySegments`)
- **VoiceOver**: "목소리 높이 그래프, 가로축 1분" + "녹음 시작부터 0:35"(다시 듣기 중에는 "재생 위치 0:05")
- 검증
  - 테스트 142개 모두 통과 (새 8개: 오른쪽 끝 = 지금, 오래 녹음한 뒤의 구간, 보이는 구간 = 남긴 소리 = 요약 구간, 시작선·n번째 선 위치와 글자, 남긴 녹음의 가로축, 눈금 간격, 눈금 글자, 점 묶기). 빌드 경고 0
  - 시뮬레이터(iPhone 18 Pro): 합성 문장 파일 1분(10초 간격 눈금, 재생 위치 선, 뒷부분 흐리게)·3분(30초 간격, 점 묶기)으로 확인. 마이크(무음)로 녹음해 "시작" 실선과 시간 눈금이 오른쪽에서 왼쪽으로 흐르는 것, 다시 녹음할 때 "2번째" 점선 확인. 대본 읽기 모드에서 대본 약 7줄
  - iPhone 17e: 대본 읽기 모드에서 보통 글자 6줄, 가장 큰 글자(접근성 최대)에서도 대본 상자 안에 약 6줄이 보인다
  - 확인 못 한 것: 실제 목소리로 흐르는 모습과 3분일 때의 부드러움 (DEVICE_TEST 3-2b·3-2c에 방법을 적음)

## [높이] 음량 막대 + 공명 밝기 막대 (2026-10-25)
아이폰 테스트 피드백: 대본을 읽는 동안 공명 같은 다른 측정이 없다 ([모음] 탭 모음 지도는 모음을 길게 낼 때만 의미가 있다).
- **음량**: 분석 조각마다 RMS를 dBFS(20·log₁₀ RMS)로 재어 피치 점에 함께 담는다. 그래프 아래 막대(−60~0 dBFS)와 숫자로, 최근 0.3초를 세기(RMS²)로 평균해 보여 준다. 크다·작다 평가 문구는 없다. 아주 큰 소리가 이어질 때만 "소리가 꽤 커요. 목에 무리가 없는지 확인해 보세요." (원칙 4)
  - 큰 소리 기준(임시값): 최근 3초 동안 점의 80% 이상이 −10 dBFS 이상. 이유: 0 dBFS는 마이크가 받을 수 있는 최대라, 그보다 10 dB 아래는 보통 말하는 크기로는 닿지 않는다고 보았다. 숨 쉬는 짧은 틈(20% 미만)은 봐준다. 아이폰 `.measurement` 모드의 실제 값을 모르므로 DEVICE_TEST 3-2d로 확인해 고친다
  - 안내 문구에 "마이크마다 값이 달라서 귀로 듣는 절대 데시벨(dB SPL)이 아니에요"
- **공명 밝기**: 목소리와 포먼트가 잡힌 최근 2.5초 점들의 F2 중앙값을 "어두운 ↔ 밝은" 막대 위 분홍 점으로. 점이 20개(약 0.4초)보다 적으면 보이지 않는다
  - 막대 가운데(보라 눈금)는 ‘내 목소리 재기’ 때의 F2 중앙값. 기준을 잴 때 F2도 함께 재어 저장한다(`baselineF2Hz`, 기준 이력 `BaselineRecord.f2MedianHz`). 막대 양 끝은 기준에서 반음 ±6개
  - 기준이 없으면 막대 대신 "내 목소리 재기를 하면 기준이 생겨요"와 F2 숫자만
  - 성별 평균·좋고 나쁨 표현 없음 (원칙 3). 한계 안내: "문장 속 공명은 어떤 모음을 말했는지에 따라 달라져요. 같은 대본을 읽을 때 비교하면 정확해요." 목소리가 높아 F1이 불확실하면(모음 지도와 같은 규칙) 속이 빈 점
- **저장(화면 추가 없음)**: F2 중앙값을 녹음 묶음(`RecordedTake.f2Median`), 연습 기록(`PracticeSession.f2MedianHz`), 남긴 녹음(`SavedRecording.f2MedianHz`), 기준 이력에 저장한다. 나중에 [기록] 탭 공명 추이에 쓴다. 저장소에 빈 칸 세 개가 더해지는 가벼운 이동이라, 예전 형식 저장소(연습 33개·녹음마다 101개)를 새 빌드로 열어 그대로 읽히는 것을 확인했다

## [높이] 큰 그래프 + 세로축 = 목표 범위 ±50 Hz + 녹음을 파일로 저장 (2026-10-25)
사용자 요청: "그래프를 크게", "설정한 밴드 기준으로 ±50 Hz 정도로", "녹음한 파일을 휴대폰에 저장할 수 있도록".
- **그래프 크기**: 고정 높이(220pt, 대본 읽기 150pt) 대신 쓸 수 있는 화면 높이의 45%(대본 읽기 33%)로. 작은 화면에서도 220·150pt 이상, 큰 화면에서도 380·280pt 이하 (`PitchGraphView.graphHeight`). iPhone 17e에서 약 272pt(대본 읽기 약 198pt)
- **세로축 = 목표 범위 ±50 Hz** (`PitchScale.graphRange`): 분석 범위 70~400 Hz 안으로 자른다 (예: 목표 135~175 Hz → 85~225 Hz, 90~120 Hz → 70~170 Hz). 목표 범위가 없으면 70~400 Hz 전체. 세로축이 좁아져 눈금은 5개 이상(예: 90·100·125·150·175·200). 기준 점선은 축 안에 있을 때만 긋는다. VoiceOver에 "세로축 85에서 225 Hz"를 더했다
- **세로축 밖**: 위·아래 끝에 붙여 회색 점선으로 그린다 (`PitchScale.isBeyond`). 처음에는 끝에 붙인 실선이었는데, 시뮬레이터에서 보니 "그 높이로 평평하게 냈다"로 읽혀서 점선으로 바꿨다. 실제 값은 큰 숫자와 요약 카드에 나온다
  - 점선이 처음에 실선으로 보였다: 선을 점 사이 조각(약 0.7pt)마다 따로 그려 점선 무늬가 조각마다 처음부터 시작했다. 조각을 한 선으로 이었는데도 그대로였던 까닭은 SwiftUI `Path.currentPoint`가 Float 정밀도로 돌아와 같은 점인지 비교가 늘 틀렸기 때문. 끝점을 따로 기억해 고쳤다
- **배치**: 그래프가 커져서 ‘말하는 언어’ 줄을 문장 카드 아래로, 막대 보는 법 안내를 맨 아래로 옮겼다 (첫 화면에 문장 카드가 더 보이게)
- **파일로 저장** (m4a, AAC 64 kbps): 요약 카드의 ‘파일로 저장’(방금 녹음)과 [기록] → 남긴 녹음의 ‘파일로 저장’. iOS 파일 저장 창(`fileExporter`)에서 사용자가 저장할 곳(나의 iPhone, iCloud Drive 등)을 직접 고른다 (원칙 2 문구에 "파일 저장 창"을 더함). 처음 이름은 "Ullim-날짜-시각" (`Views/AudioFileDocument.swift`). 같은 이름이 있으면 iOS가 ‘대치 / 둘 다 유지’를 묻는다
  - 시뮬레이터에서 찾은 버그: 형식을 `UTType.mpeg4Audio`로 두니 저장된 파일이 `.mp4`였다 (이 형식의 기본 확장자가 mp4). m4a 형식(`com.apple.m4a-audio`)으로 바꿔 `.m4a`로 저장되는 것을 확인하고, 확장자 테스트를 더했다
  - 방금 녹음은 앱의 임시 폴더에 m4a를 만든 뒤 넘긴다. 다음에 만들 때 지난번 임시 파일은 지운다

## 구절별 문장 끝 분석 1단계: 분석 계산 (2026-10-25)
실제 녹음을 보니 목표 범위를 벗어나는 구간 대부분이 문장 끝 0.3초에 몰려 있었는데, 요약 카드의 숫자(중앙값·범위·목표 안 비율)로는 보이지 않았다. 그래서 녹음을 구절로 나눠 문장 끝마다 얼마나 내려갔는지 재는 계산을 만들었다. 한국어 평서문(~다, ~습니다)은 원래 끝이 내려가므로 목표는 "평평하게"가 아니라 "하강 2~3반음 이내, 끝 바닥이 목표 하한 아래로 안 내려가기"다. 화면·요청문은 3단계.
- 기준값 `VoicePractice/Models/PhraseEndingRules.json`: iOS는 앱 번들에서(대본 JSON과 같은 방식, 못 읽으면 nil), 웹은 import로 같은 파일을 읽는다. 웹 개발 서버 허용 목록에 이 파일 하나를 더했다(사용자 승인)
- iOS `Models/PhraseEndingAnalysis.swift`, 웹 `src/dsp/phraseEnding.ts`(줄 단위로 옮김). 피치 검출(YIN)은 건드리지 않았다
  - 점 간격은 10 ms가 아니라 2048샘플 창을 절반씩 미는 간격이라(48 kHz 21.3 ms, 44.1 kHz 23.2 ms, 16 kHz 파일 64 ms) 녹음마다 이웃한 점의 시각 차이 중앙값으로 알아낸다
  - 구절: 이웃한 유성 점 사이 무성음 길이(시각 차이 − 한 칸)가 250 ms 이상이면 끊는다. 유성 점 수 × 간격이 200 ms보다 짧은 구절은 버린다
  - 구절마다: 전체 중앙값, 끝 300 ms(마지막 유성 점에서 거슬러) 중앙값·10번째 백분위수(바닥), 하강 폭 12·log₂(전체 ÷ 끝) 반음, 끝 바닥 < 목표 하한, 종류(≤ −2 rise, ≤ 3 stable, ≤ 5 falling, 그 위 dropping), 긁히는 소리 가능성(끝 300 ms에서 max(100 Hz, 중앙값 × 0.55)보다 낮은 점이 10 ms 기준 5개 = 50 ms 이상 이어짐 → 실제 간격으로 올림, 48 kHz에서 3개)
  - 백분위수·반음은 요약 카드와 같은 `PitchSummary.percentile`·`PitchScale.semitones`
  - 녹음 전체: 구절 수, 하강 폭 평균, falling+dropping 수·비율, 끝 바닥이 목표 하한 아래인 구절 수, 긁히는 소리 가능성 구절 수, 목표 밖 유성 점 중 문장 끝에 든 비율(분모는 버린 구절까지 포함한 전체, 요약 카드의 ‘목표 범위 안’과 같은 기준). 견줄 기준으로 "전체 유성 점 중 문장 끝에 든 비율"도 계산한다
- 확인
  - iOS 시뮬레이터 빌드 성공(경고 0), Swift 6 엄격 모드 빌드 성공(오류·경고 0), 기준값 JSON이 앱 안에 들어간 것 확인
  - 웹: svelte-check 오류·경고 0, 기존 테스트 262개 통과, 빌드 성공
  - 간이 점검(합성 점, 48 kHz 간격): 200 Hz 1초 + 끝 300 ms를 4반음 아래로 → 하강 4.00반음 ‘falling’, 끝 바닥이 목표 하한(170 Hz) 아래 / 180 Hz + 끝 90 Hz 6점 → 하강 0 ‘stable’이지만 바닥 90 Hz·긁히는 소리 가능성 / 0.15초 구절은 버림 / 무성음 0.3초에서 구절이 나뉨. 손으로 계산한 값과 같았다
  - 확인 못 한 것: 정식 테스트(2단계), Swift·웹 결과가 같은지(2단계의 같은 입력 파일로), 실제 목소리

## 구절별 문장 끝 분석 2단계: 테스트 (2026-10-25)
합성 피치로 1단계 계산을 확인하고, iOS와 웹이 같은 결과를 내는지 같은 입력 파일로 확인한다.
- 입력·기대값 파일 `VoicePracticeTests/PhraseEndingCases.json` 하나를 iOS(`PhraseEndingAnalysisTests`)와 웹(`web/test/phraseEnding.test.ts`)이 같이 읽는다. 둘 다 같은 기대값을 1e-9 안에서 통과하면 서로 같은 결과다
- 파일은 `Tools/PhraseEndingCases/make_cases.py`가 만든다. 점 간격은 앱과 같은 48 kHz 1024샘플(21.3 ms). 기대값은 앱 코드를 돌린 값이 아니라 경우마다 손으로 셈한 값이고, 셈은 스크립트 주석에 적었다
- 합성 피치 9가지: 요청한 6가지(평평, 4반음 하강 → falling, 질문형 3반음 상승 → rise, 끝 90 Hz 6점 → fry, 무성음 256 ms로 나뉜 두 구절, 192 ms 구절은 버리고 213 ms 구절은 남김) + 경계 3가지(무성음 234 ms는 한 구절, 목표 범위 없음 → 목표 관련 값만 null, 목소리 없음 → 구절 0)
  - fry 경우에는 무성음 한 점이 끼어 90 Hz가 2점씩만 이어진 구절을 함께 넣어, 낮은 점 수가 아니라 ‘이어진’ 수를 센다는 것도 확인한다
  - 짧은 구절 경우는 버린 구절의 목표 밖 점이 분모에 들어가는지(→ 비율 0.0) 확인한다
- 그 밖에: 앱 안의 기준값 파일이 저장소 파일과 같은지, 종류 경계(−2·3·5반음은 아래 종류에 듦), fry 연속 기준 환산(10 ms → 5점, 25 ms → 2점, 48 kHz → 3점, 44.1 kHz → 3점, 16 kHz → 1점)
- 확인
  - iOS 테스트 161개 모두 통과 (새 4개). 웹 테스트 275개 모두 통과 (새 13개), svelte-check 오류·경고 0
  - 확인 못 한 것: 실제 목소리 녹음 (3단계 화면이 생긴 뒤 아이폰·브라우저에서)

## 구절별 문장 끝 분석 3단계: 요약 카드와 AI 요청문 (2026-10-26)
1·2단계의 계산을 화면과 요청문에 붙였다. iOS와 웹이 같은 글을 쓴다.
- 글(`Models/PhraseEndingText.swift` ↔ `web/src/text/phraseEnding.ts`): 글 속 기준 숫자(3반음, 0.3초, 0.25초, 아래 10%)는 `PhraseEndingRules.json`에서 가져온다. 이를 위해 분석 결과에 기준값과 목표 범위를 함께 담았다
  - 요약 한 줄: "문장 끝 11개 중 7개가 3반음 넘게 내려갔어요" / "… 3반음 넘게 내려간 곳은 없어요" / 구절이 없으면 "문장으로 나눌 만큼 목소리가 이어진 곳이 없어요"
  - 숫자 줄(해당할 때만): 평균 하강, 바닥이 목표 하한 아래로 내려간 끝 수, "목표 범위 밖 순간의 72%가 문장 끝 0.3초에 있어요 (문장 끝은 목소리의 20%)", 긁혔을 수도 있는 곳(높이를 잘못 읽었을 수도 있다고 함께)
  - 안내: "끝이 내려가는 건 자연스러워요. 바닥이 목표 하한 아래로 내려가지 않게만 해 보세요." (목표 범위가 없으면 "3반음 안쪽으로만 내려가게 해 보세요.")
  - 구절 한 줄: 번호·종류(안정·올라감·내려감·크게 내려감), 구절 중앙값 → 끝 중앙값 Hz, 녹음 처음부터의 시간·"2.4반음 내려감"·바닥이 목표 하한 아래·긁혔을 수도 있어요
- 화면: [높이] 요약 카드의 숫자 아래에 문장 끝 칸(iOS `PhraseEndingSection`, 웹 `PhraseEndingList`). 구절 목록은 ‘구절별로 보기 (n개)’를 펼쳐야 보인다(카드가 길어지지 않게). 종류별 색은 화살표에만: 안정 회색, 올라감 청록, 내려감 연한 주황, 크게 내려감 주황 (CLAUDE.md 색)
- AI 요청문: 녹음 하나의 요청문(요약 글만·녹음과 함께·요약 복사)에 수치 아래 "문장 끝 (…)" 단락 — 구절 수, 평균 하강 폭, 3반음 넘게 내려간 구절 수·비율, 끝 바닥이 목표 하한 아래인 구절 수, 목표 밖 순간 중 문장 끝 비율과 기준 비율, 긁히는 소리 가능성 구절 수, "한국어 평서문은 끝이 내려가는 게 자연스러우니 … 하강 폭 3반음 이내, 끝 바닥이 목표 하한 아래로 내려가지 않는지로 봐 주세요". 구절이 없으면 예전 요청문 그대로. 연습 기록의 요청문과 기록 저장에는 아직 넣지 않았다
- 확인
  - iOS 테스트 164개(새 3개: 글 2, 요청문 1)·웹 테스트 278개(새 3개) 모두 통과, Swift 6 엄격 모드 빌드 오류·경고 0, svelte-check 오류·경고 0, 웹 빌드 성공. 두 쪽이 같은 문장을 기대한다
  - 웹 미리보기(375×812, 밝은·어두운 모드)와 iOS 시뮬레이터(iPhone 17e)에서 합성 녹음으로 확인: 계단 모양 끝 4개(3.9반음 내려감·6.2반음 크게 내려감·3.2반음 올라감·안정 + 끝 90 Hz) → "문장 끝 4개 중 2개가 3반음 넘게 내려갔어요", 평균 1.7반음, 긁혔을 수도 있는 곳 1개, 화살표 색 4가지. 두 쪽 숫자가 같았다. 웹 요청문 전체도 확인. 콘솔 오류 없음
